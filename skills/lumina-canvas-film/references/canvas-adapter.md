# Lumina capability adapter

The library's creative workflow and 51 style specifications are authoritative. This adapter changes tool bindings and output reporting to fit the current Lumina session; it does not relax the selected style's grammar.

## Discover actual capabilities

Check tool descriptions for native questions, canvas inspection, drawing/updates, files, code execution, rendering, audio, video, and export. Use actual schemas. An embedded engine example or a source command is documentation, not proof that the engine or shell exists in this session.

If the host has files/code execution and the library, follow the source technique. If it has canvas drawing only, produce the treatment, model/style frames, and scene composition with camera/timing/sound notes where useful. Say that this is a storyboard or production plan, and that the code-rendered film pipeline has not run. If the user requires the full movie, identify the specific missing capability and ask for the execution environment; do not silently substitute an image or storyboard for the requested movie.

## Keep style fidelity

Read all fragments for the chosen slug before drawing. Extract a working checklist for material/rendering, color, type, motion, camera, sound, native moves, pitfalls, and evidence rules. Enforce fixed requirements and choose among that style's documented variation space. Do not replace named styles with generic “cinematic,” omit evidence rules, or use unrelated textures as a substitute for the medium.

A still storyboard can show key poses, framing and composition, with motion arrows or concise cue notes representing time-based requirements. Label these as planned rather than executed. When a critical medium property cannot be represented by the available tools, explain the precise mismatch; get a user decision to change output mode or style instead of claiming exact reproduction.

## Source-relative links and engines

The full STYLE documents preserve source-relative `demo/`, `DEMO.md`, `core/` and code references. They do not point inside the import package. Resolve them under the pinned library location recorded in `style-manifest.json`, for the selected `styles/<slug>/` directory, using only available file/network tools. Do not assume a remote path is mounted locally. Do not open demos until the original treatment exists.

Library install/setup and engine code remain in the repository, outside this text-only import package. Follow `technique.md` only where execution is actually available. Treat pasted example code as illustrative until its dependencies are present.

## Canvas construction and review

Inspect the existing canvas before changes; preserve unrelated content. Give a delegated drawing agent a complete brief: confirmed topic and slug, full selected style invariants, treatment, exact visible text, layout, timing/camera/sound notes, and check criteria. Topic/style selection happens before production, through the real native question tool.

Use supported editable elements where they express the required medium. Arrange scene frames with clear reading order, enough whitespace, stable labels, and readable subject scale. Inspect generated results for the source pitfalls: tiny subjects, darkness, same-color overlap, subtitles over action, unreadable pacing, blank transitions, and tracking errors where animation exists.

Run only checks the tools actually support and report any incomplete review. `agents/openai.yaml` supplies optional OpenAI-compatible interface metadata; Lumina may ignore it. All operational requirements, including native questions, are in `SKILL.md` and the reference documents.
